# ADR 0002：一期 Redis、后台任务与锁策略

- 状态：已接受
- 日期：2026-08-24
- 决策范围：一期产品化基础设施

> 实施状态：已实现 Redis 登录 IP/账号双桶限流及失败关闭；
> `background_jobs` 事实表已落库。Celery worker、outbox/补偿投递、
> Query/Agent 限流、缓存和任务 API 仍未实现，不得将本 ADR 描述的
> 目标形态当作已交付能力。

## 背景

当前应用是模块化单体：React 前端调用 Gunicorn 托管的 Flask API，API 通过
SQLAlchemy 访问 MySQL，并在自然语言分析请求中同步调用外部 LLM。普通聚合查询
有明确的字段、行数和执行时间上限，但 Agent 请求需要执行“模型规划、数据库查询、
模型解读”多段链路。全量数据导入、报告生成等工作也会明显长于普通 HTTP 请求。

继续把这些工作放在同步 WSGI worker 中会带来以下问题：

- 少量慢请求即可占满 Gunicorn worker，影响登录、权限管理和普通查询。
- HTTP 超时、客户端断开和进程重启会使任务状态不透明，并诱发重复执行。
- 多个 API/worker 进程无法依靠进程内状态统一完成限流、缓存和任务协调。
- SQLAlchemy 默认连接池会随 API 进程和任务 worker 数量相乘，可能耗尽 MySQL
  连接数。
- 把业务唯一性或任务正确性寄托在有租约的缓存锁上，会在超时、故障转移或进程暂停时
  破坏数据一致性。

一期需要解决上述问题，但不以微服务、复杂事件平台或多套中间件扩大交付范围。

## 决策

一期保持模块化单体，增加一个 Redis 实例和 Celery worker。MySQL 仍是所有业务与任务
状态的唯一事实源；Redis 只承担可过期、可重建或可补偿的能力。

```text
Browser
  -> Gunicorn / Flask API
       -> MySQL（用户、权限、审计、任务状态、分析数据）
       -> Redis（缓存、限流、短期会话、Celery broker）
       -> 创建后台任务并返回 202 + job_id

Celery worker
  <- Redis broker
  -> MySQL 领取/更新任务
  -> MySQL 聚合查询或批量导入
  -> 受控 LLM 调用
  -> MySQL 保存最终状态和受限结果
```

不在一期拆分独立的认证、查询或 Agent 微服务。模块边界继续遵循
`API -> service -> repository -> storage/client`，Celery task 只负责恢复请求上下文、
调用 service 和更新任务状态，不直接承载业务规则。

## 同步与异步边界

以下操作继续同步执行：

- 登录、登出、令牌刷新、用户与角色管理；
- schema 和受限 distinct 查询；
- 已通过权限、隐私、成本和超时校验的普通聚合查询；
- 任务状态读取和取消请求。

以下操作进入后台队列：

- 包含一次或多次 LLM 调用的 Agent 分析；
- 全量数据清洗、导入、索引或汇总表重建；
- 报告和大文件导出；
- 需要重试、进度展示或可能超过普通 HTTP 时限的批处理。

任务创建接口返回 HTTP `202` 和 `job_id`。一期由前端轮询任务状态；只有在轮询产生了
可观测的性能问题后，才考虑 SSE。WebSocket 不属于一期依赖。

至少划分 `agent`、`imports` 和 `reports` 三类逻辑队列。导入队列默认并发为 1；Agent
队列并发受上游模型额度和数据库连接预算共同约束，不能简单等同于 CPU 核数。

## MySQL 的事实源职责

MySQL 持久保存：

- 用户、凭据摘要、会话或 refresh token 摘要、角色和权限；
- 安全审计、数据批次、质量报告和数据版本；
- 后台任务状态、执行阶段、进度、重试次数和最终结果引用；
- 业务幂等记录和所有必须强一致的唯一性约束。

Redis 中的会话、缓存、限流计数和 broker 消息不得取代这些持久记录。Redis 数据丢失
可以导致缓存冷启动、用户重新登录或任务重新投递，但不得导致权限提升、任务永久丢失、
重复入库或审计记录消失。

## Redis 的一期职责

### 缓存

仅缓存已完成权限校验、聚合校验和最小分组隐私保护的结果：

- schema：较长 TTL，例如 1 小时；
- distinct 值：中等 TTL，例如 5 至 30 分钟；
- 受限聚合结果：短 TTL，例如 1 至 5 分钟，依据压测调整。

聚合缓存键至少包含：规范化 QuerySpec 哈希、数据范围或租户范围、权限版本、数据版本、
隐私规则版本和接口版本。成功完成数据导入时递增数据版本，使旧缓存自然失效；不得通过
全库 `SCAN`/`KEYS` 删除实现主要失效策略。

不得缓存患者级结果、模型原始响应、完整医疗问题或未经净化的错误。缓存故障时普通只读
查询可以旁路到 MySQL，但仍必须执行权限、隐私和成本校验。应对高成本缓存重建增加短期
single-flight 锁和 TTL 抖动，避免缓存击穿。

### 限流与并发配额

使用 Redis 原子计数或 Lua 脚本实现滑动窗口或令牌桶。至少覆盖：

- 登录：同时按来源 IP 和账号标识限流；
- Agent：按用户、组织和上游模型全局额度限制请求频率与并发数；
- 聚合查询：按用户及查询成本分级限制；
- 导入、导出和管理接口：按角色和操作类型限制。

具体限值必须配置化，并在压测和实际使用数据基础上调整。触发限制时返回稳定的 HTTP
`429` 和 `Retry-After`。Redis 不可用时，缓存可以降级，但登录、Agent、导入等安全或
成本敏感入口不得静默无限放行，应安全失败并返回 `503` 或使用明确受限的本机兜底。

### 会话

如果采用服务端会话，Redis 可以保存短期会话数据和注销/撤销标记；用户状态、权限、
凭据摘要和长期 refresh token 摘要仍保存于 MySQL。缓存的授权结果必须包含权限版本并
使用短 TTL，用户禁用或角色变更后必须立即递增权限版本或删除对应会话。

Redis 中不得保存明文密码、API 密钥、患者级数据或长期有效令牌。

### Celery broker

Redis 作为一期 Celery broker。消息正文只包含 `job_id`、任务类型和必要的关联 ID；
worker 根据 `job_id` 从 MySQL 读取任务输入。不得把完整问题、医疗数据、查询结果或密钥
放入 broker 消息。

Celery 采用至少一次投递语义，并配置：

- worker 完成任务后确认消息；
- 有界重试和指数退避；
- soft/hard time limit；
- 大于单次任务上限的 visibility timeout；
- 长任务较低的 prefetch，避免单 worker 囤积任务；
- worker 丢失后的重新投递和 MySQL 状态补偿。

Redis/Celery result backend 不能作为长期结果存储。API 查询的任务状态和结果以 MySQL
为准；较大的报告文件在后续接入受控对象存储，并在 MySQL 中保存引用和校验信息。

## 任务表、投递和幂等

`background_jobs` 至少记录：

- `job_id`、任务类型、队列、所有者和可选组织/数据范围；
- `status`、执行阶段、进度、attempt/max_attempts；
- 输入引用或净化后的输入、payload 哈希、幂等键；
- request ID、worker ID、heartbeat、创建/开始/结束/更新时间；
- 安全错误码、结果摘要或结果引用；
- 用于乐观并发控制的 `version`。

同一作用域内建立类似
`UNIQUE(owner_id, job_type, idempotency_key)` 的约束；存在组织/租户时将其加入唯一作用域。
客户端重试同一写请求时返回已有任务，不再次创建、扣减配额或重复执行。

任务投递遵循以下顺序：

1. 在 MySQL 事务中创建任务和 outbox 记录；
2. dispatcher 把 outbox 事件发布到 Redis broker；
3. 发布成功后标记 outbox；
4. 补偿扫描器重新处理超时或未发布的 outbox；
5. worker 使用条件更新原子领取任务，例如只允许 `queued/retry -> running`；
6. worker 按阶段保存进度，重试从最后一个已确认阶段继续；
7. 成功、失败或取消均写回 MySQL，并保留安全的审计信息。

如果首个实现暂缓独立 outbox 表，也必须先提交 MySQL 任务记录再入队，并提供定时扫描
`queued` 且未被领取任务的补偿机制；不能只依赖一次 Redis publish。

全量导入使用源文件哈希/批次 ID 唯一约束、staging table、分批事务和 checkpoint。
完成行数、拒绝行数、文件哈希和关键聚合核对后再事务性切换可见数据，避免单个超大事务
和部分成功状态。

## 锁与并发控制

### 必须使用数据库约束或事务的场景

以下正确性要求不得依赖 Redis 分布式锁：

- 用户名、邮箱、用户角色、refresh token 和幂等键唯一；
- 用户禁用、权限变更、任务状态流转和硬配额扣减；
- 同一数据源/批次防重复导入；
- 审计追加、数据写入和 schema 迁移；
- 任何锁失效后可能造成越权、重复写入、数据损坏或不可逆副作用的操作。

这些场景使用 MySQL `UNIQUE`/外键/检查约束、事务、条件 `UPDATE` 和受影响行数判断；
对少数高竞争强一致计数使用 `SELECT ... FOR UPDATE`，对用户资料、角色和任务状态优先
使用 `version` 乐观锁。任务抢占通过状态条件更新完成，不额外获取分布式锁。

### 可以使用 Redis 短租约锁的场景

仅在丢锁会造成重复计算但不会破坏业务正确性时使用：

- 缓存 single-flight 和热点缓存刷新；
- 定时补偿扫描器或缓存预热器的单实例执行；
- 非关键报告重复计算抑制；
- 以数据库约束为最终防线时的快速并发削峰。

Redis 锁必须使用唯一 owner token、`SET key token NX PX`、有限 TTL，以及校验 owner 后
删除的 Lua 脚本。执行时间可能超过 TTL 时需要受控续约。不得使用裸 `SETNX` 后无条件
`DEL`，不得使用无期限锁，也不得把单 Redis 锁描述为强一致分布式锁。若操作需要 fencing
token 才能保证写入安全，应把最终并发控制放回 MySQL，而不是在一期引入 Redlock。

数据库迁移由部署流水线中的单次迁移步骤执行，不使用应用级 Redis 锁协调。

## MySQL 连接池与查询性能

API 进程和 Celery worker 各自建立 SQLAlchemy engine，禁止在 fork 前建立并继承活动连接。
显式配置并记录：

- `pool_size`、`max_overflow`、`pool_timeout`、`pool_recycle`；
- `pool_pre_ping`、连接超时和查询执行超时；
- API 与不同任务队列的并发数。

部署预算必须满足：

```text
API 进程最大连接数
+ 所有 Celery worker 最大连接数
+ 导入/迁移/监控保留连接
< MySQL max_connections 的安全预算
```

API 使用只读或最小权限数据库账号；导入、迁移和管理任务使用隔离的写账号。慢查询优先
通过 `EXPLAIN`、复合索引、查询上限和预聚合表解决，Redis 缓存不能替代正确的数据模型
和索引。只有在索引、汇总表和查询治理完成后仍有持续读压力，才评估只读副本。

## 健康探针

健康检查拆分为：

- liveness：仅证明 Flask 进程和事件循环可响应，不访问外部依赖；
- readiness：使用 `SELECT 1` 检查 MySQL，并按当前路由能力检查 Redis；
- dependency/status：展示 MySQL、Redis、worker heartbeat 和 LLM 的可用/降级状态，供运维
  使用，不作为高频负载探针。

健康探针不得执行全表 `COUNT(*)`、真实 LLM 请求或高成本聚合。LLM 暂时不可用时，普通
数据库分析仍可服务，状态应标为 degraded；MySQL 不可用时查询服务不就绪。Redis 不可用
时普通缓存查询可以降级，但后台任务、跨实例限流和服务端会话相关能力不就绪。

## 可观测性要求

request ID 必须从 API 传递到 MySQL 任务记录、Celery header、worker 日志和外部调用。
日志只记录请求/任务标识、用户或组织的不可逆标识、耗时、聚合行数和错误类别，不记录
完整问题、患者级字段、查询结果、令牌或连接串。

一期至少监控：HTTP 延迟和错误率、MySQL 池使用与等待、慢查询、Redis 延迟/命中率/
内存/eviction、队列深度与最老任务年龄、worker heartbeat、任务重试/失败、LLM 延迟/
429/5xx/成本、登录失败与限流次数、导入吞吐和拒绝条数。

## 故障与降级原则

- Redis 缓存故障：旁路缓存，执行有上限的 MySQL 查询。
- Redis broker 故障：停止接收新后台任务并返回 `503`；已创建但未发布的任务由 outbox
  或补偿扫描恢复。
- worker 故障：消息重新投递，MySQL lease/heartbeat 识别陈旧的 `running` 任务；幂等
  handler 防止重复副作用。
- MySQL 故障：认证、权限、查询和任务状态不可安全运行，readiness 失败。
- LLM 故障：Agent 任务按策略重试并安全失败；已完成的聚合查询结果不因可选文字解读失败
  而丢失。

## 升级触发条件

### Redis broker 升级到 RabbitMQ

只有出现以下一项或多项经过监控确认的需求时才升级：

- broker 消息持久性、确认语义或恢复时间已成为明确 SLA，MySQL outbox 加补偿投递仍不能
  满足；
- 需要复杂路由、优先级、死信交换、多个独立服务消费或严格隔离的队列治理；
- Redis visibility timeout、长任务重投或大规模积压反复造成实际故障；
- Redis 同时承载缓存、会话和 broker 后，资源隔离无法通过独立实例或容量治理解决。

升级 broker 不改变 MySQL 任务事实源和幂等要求。

### 引入 Kafka

Kafka 只在需要可回放的事件流、多个独立消费者、持续高吞吐数据变更或 CDC/流式分析时
引入。Kafka 不作为一期 Celery 任务队列，也不因为住院表达到数百万行就自动引入。

### Redis 高可用

一期使用单实例或单个托管 Redis。只有 Redis 故障已影响约定可用性目标、会话/任务恢复
时间不能接受，或监控显示单实例内存、吞吐、延迟长期接近安全上限时，才升级：

1. 优先采用托管主从或 Sentinel，实现故障转移；
2. 缓存、broker、会话/限流先做逻辑和容量隔离；
3. 只有数据量或吞吐确需分片时才采用 Redis Cluster。

Redis HA 不提升 Redis 锁到业务强一致锁，也不改变 MySQL 的事实源地位。

## 暂不采用

一期明确不采用：

- 认证、查询和 Agent 微服务拆分；
- Kafka 作为任务队列；
- RabbitMQ 与 Redis broker 同时存在；
- Redlock、分布式事务和跨系统两阶段提交；
- Redis Cluster、多区域 Redis 或数据库读写分离；
- 仅凭增加 worker 数量规避慢查询和同步 Agent 阻塞。

## 影响

正向影响：

- 只新增 Redis 这一种基础服务，同时覆盖缓存、跨进程限流和一期 broker；
- 长任务不再占用 WSGI worker，API 容量与任务并发可以分别控制；
- MySQL 任务表、outbox 和幂等处理使至少一次投递可恢复、可审计；
- 锁的使用范围被限制在非关键协调，业务一致性可由数据库验证。

代价与风险：

- Redis 和 Celery 增加部署、告警、容量与故障演练工作；
- Redis broker 不是最终的高可靠消息平台，需要 outbox、补偿扫描和幂等 worker 弥补；
- 缓存存在短期陈旧，需要数据版本、权限版本和隐私规则版本共同控制；
- 后台任务 API 需要新的状态模型、取消语义和前端轮询状态。

这些代价小于在一期同时引入 RabbitMQ、Kafka、分布式锁服务和微服务体系的复杂度，并为
后续替换 broker、扩展 worker 或增加 Redis HA 保留了清晰边界。
